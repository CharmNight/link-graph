# Link Graph 工作台重构设计

日期：2026-04-10

## 1. 背景

当前 Link Graph 在交互语义上偏向“结果展示器”：

- `讲解` 更像一次性摘要生成
- `审计` 更像结构化报告加 patch 建议
- `草稿` 更像 patch 的附属物
- `代码生成` 没有被强约束为基于“已确认业务流程”

这和项目目标不一致。项目目标不是单纯产出 AI 文案，而是解决 AI 编码时对业务流程理解丢失的问题，形成“可检查、可讨论、可确认、可生成”的链路工作台。

## 2. 目标

本次重构要把产品模型统一为：

- `讲解 = 步骤化阅读器`
- `审计 = 多轮聊天器`
- `草稿 = 统一业务真相层`
- `生成 = 基于草稿层`

具体目标：

1. 用户能看到一套稳定步骤，而不是一段静态总结。
2. 用户能围绕某一步继续追问，并按需下钻到被调方法。
3. 用户能通过审计聊天逐条提出、讨论、确认业务修改。
4. 已确认的业务修改统一沉淀到草稿层，而不是散落在聊天文本或结果卡片里。
5. 后续计划与代码生成只能基于草稿层，不允许直接基于聊天内容自由发挥。

## 3. 非目标

- 不保留旧“结果面板报告式展示”作为长期兼容路径。
- 不做双轨模式、feature flag 或新旧面板并行。
- 不在本次设计中尝试直接改源码。
- 不把整页 UI 做成完全重写；保留左图右工作台的大框架。

## 4. 约束与确认结论

以下内容已和用户确认：

- 不接受中间兼容态，重构后应一次性切到新模型。
- 左侧保留图画布，右侧重构为新工作台。
- 右侧工作台采用顶部 Tab：`讲解 / 审计 / 草稿`。
- `讲解` 支持三种粒度：
  - 业务级
  - 方法调用级
  - 代码语义级
- 不同视图共用同一套步骤。
- `讲解` 追问默认围绕当前步骤回答，可主动下钻，不自动无限展开。
- `讲解` 中“添加到草稿”默认加入 `草稿说明项`。
- `审计` 默认是“每个方法/链路一条独立会话”，并支持切换为跨方法会话。
- `审计` 只有一个统一输入框。
- `待确认变更` 逐条确认，不允许自动写入草稿层。
- `草稿` 采用上下分区：
  - 上：草稿变更项
  - 下：草稿说明项
- 图上默认显示修改后，支持一键对比前后。
- 变更节点必须有颜色区分。
- 源码修改只能基于已确认草稿层。

## 5. 总体方案

采用“左图右工作台”的整体重构方案：

- 左侧继续承载事实图、流程图、资源关系图
- 右侧彻底废弃旧结果面板语义，改为新的工作台
- 统一核心模型，驱动讲解、审计、草稿和后续生成

这是一次整体切换，不做长期兼容层。

## 6. 核心模型

### 6.1 事实层

`事实层` 是从源码、资源、配置和调用关系中提取出的只读事实链路。

职责：

- 作为所有分析的原始依据
- 作为三视图投影的基础输入
- 不允许直接编辑

要求：

- 保留现有提图和投影能力
- 明确和草稿层分离

### 6.2 步骤层

`步骤层` 是基于事实层和草稿层抽象出来的统一业务步骤序列。

职责：

- 作为 `讲解` 的主对象
- 作为 `审计` 的讨论锚点
- 作为跨视图共享的语义骨架

每个步骤至少包含：

- `stepId`
- `title`
- `granularity`
- `kind`
- `description`
- `evidenceRefs`
- `nodeRefs`
- `sourceRefs`
- `downstreamTargets`
- `draftStatus`

设计要求：

- 步骤必须有稳定 ID
- 三种粒度来自同一条链路的不同抽象，不是三套互不相关的数据
- 三视图共享同一套步骤 ID

### 6.3 草稿层

`草稿层` 是统一业务真相层，是后续生成的唯一依据。

职责：

- 承接用户确认后的业务修改
- 承接从讲解中加入的业务关注说明
- 作为计划和代码生成的输入

草稿层分为两类条目：

1. `草稿变更项`
- 表示已确认的业务变更
- 可影响图语义和后续生成

2. `草稿说明项`
- 表示业务关注点、待补说明、阅读辅助信息
- 默认来自讲解中的“添加到草稿”

设计要求：

- 草稿层是唯一可编辑业务层
- 三个视图都从同一份草稿层重新投影
- 不允许每个视图维护独立草稿

### 6.4 审计会话层

`审计会话层` 表示围绕方法/链路进行的多轮聊天上下文。

职责：

- 保存会话历史
- 保存当前焦点步骤或焦点变更项
- 产出候选变更项

设计要求：

- 默认按方法/链路独立会话
- 支持切换为跨方法会话
- 不直接改源码
- 不直接写草稿层

## 7. 页面结构

### 7.1 主布局

主界面采用左右布局：

- 左：图画布
- 右：工作台

左侧图画布：

- 保留三视图切换：
  - 事实图
  - 流程图
  - 资源关系图
- 默认显示修改后结果
- 支持一键对比修改前后
- 变更节点和风险节点有明确颜色区分

右侧工作台：

- 顶部 Tab：`讲解 / 审计 / 草稿`

### 7.2 讲解 Tab

讲解 Tab 使用左右结构：

- 左：步骤列表
- 右：步骤详情

讲解 Tab 应包含：

- 粒度切换器：业务级 / 方法调用级 / 代码语义级
- 步骤列表
- 当前步骤详情
- 当前步骤证据
- 动作入口：
  - `追问这一步`
  - `继续下钻`
  - `添加到草稿`

讲解的职责是帮助理解流程，不直接修改逻辑。

### 7.3 审计 Tab

审计 Tab 使用上下结构：

- 上：会话消息区
- 下：待确认变更

审计 Tab 应包含：

- 会话切换器
- 当前会话消息流
- 单一聊天输入框
- 当前焦点标识（步骤或待确认变更）
- 待确认变更列表

待确认变更要求：

- 有稳定 ID
- 每轮聊天增量更新
- 允许：
  - 新增
  - 修订
  - 废弃
  - 已确认写入草稿
- 不允许整表重刷后丢失上下文

点选某条待确认变更后：

- 不打开第二个聊天框
- 只把它设为当前讨论焦点
- 继续使用统一输入框对话

### 7.4 草稿 Tab

草稿 Tab 采用上下两个分区：

- 上：草稿变更项
- 下：草稿说明项

草稿 Tab 应包含：

- 每条草稿项的状态
- 变更前后对比入口
- 影响步骤/节点范围
- 来源信息（来自哪轮审计会话或哪一步讲解）

设计要求：

- `草稿变更项` 主次高于 `草稿说明项`
- 用户应能清楚知道后续代码生成依赖的主要是草稿变更项

## 8. 交互流程

### 8.1 讲解流程

1. 加载事实层
2. 生成步骤层
3. 用户浏览步骤列表
4. 用户查看某一步详情
5. 用户可执行：
   - 追问该步骤
   - 下钻被调方法
   - 添加到草稿说明项

### 8.2 审计流程

1. 打开当前方法/链路的审计会话
2. 用户围绕链路持续聊天
3. 模型从聊天中提取候选变更项
4. 候选变更项进入待确认区
5. 用户逐条确认
6. 已确认项写入草稿变更项

### 8.3 草稿与生成流程

1. 草稿层形成当前业务真相
2. 图视图重新投影
3. 用户检查草稿结果
4. 计划生成基于草稿层
5. 代码生成基于草稿层

硬规则：

- 没有草稿确认，不允许直接生成代码修改

## 9. 候选变更项设计

候选变更项是审计聊天和草稿层之间的结构化中间对象。

每条候选变更项至少包含：

- `changeId`
- `kind`
- `targetStepIds`
- `targetNodeIds`
- `beforeState`
- `afterState`
- `reason`
- `evidenceRefs`
- `impactSummary`
- `status`

其中：

- `beforeState`：当前事实层或草稿层中的状态
- `afterState`：建议状态
- `status`：
  - `PENDING_CONFIRMATION`
  - `CONFIRMED`
  - `REJECTED`
  - `SUPERSEDED`

## 10. 颜色与可视化规则

图上至少需要以下状态颜色体系：

- 事实节点：默认事实色
- 草稿变更节点：显著高亮色
- 草稿说明节点：较轻提示色
- 风险提示节点：警示色

颜色目标：

- 一眼分辨“事实”与“草稿”
- 一眼分辨“业务变更”与“阅读说明”

图上展示规则：

- 默认显示修改后
- 提供前后对比入口
- 详情抽屉中展示修改前/后和修改原因

## 11. 数据流

### 11.1 讲解

- 输入：事实层 + 草稿层 + 粒度
- 输出：步骤列表 + 步骤详情

### 11.2 审计

- 输入：事实层 + 草稿层 + 当前会话历史 + 当前焦点
- 输出：新消息 + 候选变更项增量

### 11.3 草稿

- 输入：已确认候选变更 + 讲解加入的说明项
- 输出：统一草稿层 + 三视图重新投影

### 11.4 生成

- 输入：草稿层
- 输出：计划与代码草稿

## 12. 前端重构要求

前端应删除或废弃以下旧模型：

- 旧“讲解结果卡”摘要心智
- 旧“审计报告卡”心智
- 运行中原始 JSON 预览展示
- 将 `answer` 拆成报告段落的旧报告式布局

前端应新增：

- 步骤工作台状态
- 会话状态
- 候选变更状态
- 草稿说明项状态
- 草稿变更项状态
- 前后对比状态

## 13. 后端重构要求

后端应补足：

- 稳定的步骤模型
- 审计会话模型
- 候选变更提案模型
- 草稿层统一写入模型
- 基于草稿层的生成入口

后端应删除或弱化：

- 以“结果文本”为中心的讲解返回模型
- 以“一次性报告”为中心的审计返回模型
- 运行中原始结构化 JSON 直接回显到 UI 的机制

## 14. 异常与失败处理

- 证据不足时，不能产出伪装成事实的草稿变更
- 证据不足时，只能生成草稿说明项或风险提示
- 审计跨出当前链路范围时，应显式提示切换会话范围
- 候选变更影响范围不清晰时，保持待确认，不自动入草稿
- 草稿层覆盖事实层时，图上要明确显示冲突或覆盖关系

## 15. 测试与验收

### 15.1 讲解验收

- 能看到稳定步骤列表
- 步骤支持三种粒度
- 同一 `stepId` 可在三视图中定位
- 可围绕步骤追问
- 可主动下钻
- 可把步骤加入草稿说明项

### 15.2 审计验收

- 审计是多轮聊天，不是一次性报告
- 只有一个输入框
- 待确认变更增量更新
- 逐条确认写入草稿
- 不再显示半截 JSON 预览

### 15.3 草稿验收

- 草稿变更项和草稿说明项分层清晰
- 图上变更节点高亮
- 默认显示修改后
- 支持一键对比前后
- 三视图共享统一草稿层

### 15.4 生成验收

- 无草稿确认时不可直接生成代码
- 计划和代码生成明确依赖草稿层

## 16. 实施策略

虽然工程实现可以拆解任务，但产品交付必须是一致的新模型，一次性切换，不接受中间兼容态。

明确原则：

- 不保留旧工作流作为并行入口
- 不做长期兼容适配层
- 不做“半旧半新”的面板共存

本设计允许在开发分支中按模块实现，但最终交付必须统一切换到新工作台。

## 17. 推荐落地方式

推荐采用“右侧工作台整体重构”：

- 保留左侧图区域
- 彻底重做右侧工作台
- 新模型统一接管讲解、审计、草稿和生成链路

这是本次设计的推荐实现方向。
